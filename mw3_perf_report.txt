2. OVERALL CPU EFFICIENCY ASSESSMENT
------------------------------------------------------------------------
 IPC 1.23 is below typical Zen2/Zen3 IPC for optimized native code
 (1.5 - 2.0+). This is consistent with JIT translation overhead,
 frequent thread transitions, and the emulator's control/branch-heavy
 inner loop rather than pure data throughput.

 Cache behavior is acceptable. LLC miss rate of ~24% is not pathological
 for an emulator touching guest memory and texture pages. L1-D traffic is
 high: ~112 billion loads and ~101 billion stores in 30s, confirming a
 very write-heavy workload, likely due to guest-side texture uploads and
 memory-mapped IO.

 Branch miss rate of 1.1 M in 30s translates to ~36K mispredicts/sec,
 which is within expected range for a dynamic recompiler-driven workload
 where target addresses are discovered at runtime.

6. THREAD SCHEDULING / KERNEL TIME
------------------------------------------------------------------------
 Significant scheduler activity observed across multiple threads:
 - GPU Commands thread: ~4.3 % in sched_yield / schedule / syscall
 - Backend thread:      ~1.4 % in mprotect + TLB flush chain
 - All threads:        repeated mprotect / mprotect_fixup /
                       vma_modify/vma_modify_flags / __split_vma /
                       flush_tlb_mm_range / on_each_cpu_cond_mask /
                       smp_call_function_many_cond

 This matches Xenia's known pattern of flipping code cache pages
 between PROT_READ|PROT_WRITE|PROT_EXEC to allow JIT emission then
 execute. Each flip forces a TLB shootdown across all CPUs using TLB
 flush IPIs. This is unavoidable without changing Xenia's JIT memory
 policy, but is currently only a few percent of total CPU time and not
 the primary bottleneck.

7. CALLGRAPH ANALYSIS: WHO CALLS WHAT
------------------------------------------------------------------------
TimerThreadMain is the single largest named hot function at ~4-22%.
It sits in a single dedicated thread and burns cycles in a spin-wait.
Replacing it with a blocking wait/futex or parking the thread until the
next timer expires would measurably reduce wasted CPU. The source file
already contains comments acknowledging this exact issue at lines 29-39,
which were partially reverted for Proton/MSVC compatibility.

VulkanCommandProcessor::UpdateBindings feeds into RADV kernel-side
descriptor-set updates. The high shared-object cost means each draw
submits many descriptor writes. This path is dominated by driver work
and limited by what state Xenia feeds the driver; large gains here
usually come from reducing redundant descriptor updates rather than
in-helix optimization.

8. VERDICT / PRIORITIZED OPTIMIZATION OPPORTUNITIES
------------------------------------------------------------------------
Priority 1 - HIGH: Spin-wait TimerQueue thread burns ~4-22 % CPU for
                    no useful work. Resolve the Proton/MSVC condition_variable
                    bug in disruptorplus, or use an alternate blocking wait
                    primitive, so the timer thread can park instead of
                    consuming a full time quantum.

Priority 2 - MEDIUM: JIT code-profile hinting. The 0xa0000592 dynamic
                     stub appears repeatedly across all worker threads,
                     suggesting unresolved indirect branches or frequent
                     recompilation of the same guest blocks. Reduce re-JIT
                     churn by keeping translated block lifetime longer or
                     improving the guest TLB/cache coherence logic.

Priority 3 - LOW: Mprotect / TLB shootdowns are measurable but not the
                  primary limiter. On kernels with mglru and lazy TLB
                  shootdowns the cost is lower; do not redesign the JIT
                  memory model unless Priority 1 is completed and the
                  profile changes.

Priority 4 - LOW: IPC 1.23 might be improved with compiler vectorization
                  or reduced atomic pressure, but without a symbol-rich
                  annotated hotspot with a clear scalar loop this is
                  not actionable today.
